# River Ways — Initial Domain and Event Contracts

**Status:** Proposed contract baseline; no schema migration or runtime event bus is included  
**Date:** 10 November 2026  
**Depends on:** `PRD.md`, `architecture.md`, `rules.md`, `tasks.md`, current lead migrations and contact handler.

## 1. Purpose

Define stable concepts and boundaries shared by the public website, Rebuilder, Revenue OS, agency workforce, Creative Studio and future Avenize integration.

This document is a contract proposal, not evidence that all listed entities exist in code or production. Existing fields are labelled **Current**; new concepts are labelled **Proposed**.

## 2. Existing data contract: inbound lead

The selected integration branch currently contains:

- `migrations/0001_leads.sql`: `leads` and `lead_rate_limits`.
- `migrations/0002_lead_pipeline_attribution.sql`: stage, source, landing page, referrer and UTM fields.
- `migrations/0003_lead_operations.sql`: assignee, next action, last contacted, closed and updated timestamps; indexes, triggers and `ops_open_leads` view.
- `functions/api/contact.js`: server-side validation, rate limiting, duplicate detection, D1 persistence and Resend notification attempt.

### Current lead fields

| Field | Meaning | Notes |
|---|---|---|
| `id` | Lead identifier | UUID string generated by the contact handler |
| `name`, `email` | Enquirer identity/contact | Personal data; restrict access |
| `company` | Submitted company name | Free text, not yet a normalized Organization |
| `goal`, `details` | Submitted brief | Do not treat as a complete approved scope |
| `brief_hash` | Duplicate-detection hash | Not an identity or business key |
| `notification_status` | Email handoff state | pending / sent / failed / not_configured |
| `ip_hash` | Rate-limit hash | Never expose to client users |
| `created_at`, `updated_at` | Record timestamps | ISO strings from current handler / SQLite trigger |
| `stage` | Lead pipeline stage | new / qualified / meeting / proposal / won / lost / nurture |
| `source`, `landing_page`, `referrer`, `utm_*` | Acquisition attribution | Current schema |
| `assigned_to`, `next_action_at`, `last_contacted_at`, `closed_at` | Operational follow-up | Current schema |

The `source` column currently defaults to `website`; the contact handler accepts `website`, `campaign` or `referral`. Do not overload this field with unreviewed outbound discovery sources.

### Current limitations to preserve explicitly

- The lead record is an inbound enquiry, not a complete CRM contact, organization or client record.
- `company` is free text and is not a stable organization ID.
- The contact handler appends selected journey and engagement context to `details`; these are not currently dedicated columns in the observed migrations.
- There is no current verified tenant-membership or client-portal authorization model in these lead migrations.
- The current schema does not establish a verified payment, contract, client or project.
- Do not expose `ip_hash`, internal notification status, internal notes or other operational fields in public/client-facing projections.

## 4. Lifecycle boundaries

### Prospect → opportunity → client → project

1. A researched outbound Prospect remains separate from an inbound Lead.
2. A Lead may be linked to a Contact and Organization only after identity matching is reviewed; do not auto-merge based on a company-name string.
3. Qualification creates or updates an Opportunity with source evidence and a next action.
4. A proposal or engagement records the approved scope and commercial terms.
5. Payment verification is an explicit record with amount, currency, reference, time, verifier and evidence. Never infer payment from a message or a pipeline stage.
6. Client activation and project production eligibility are distinct states.
7. A Project is created from an approved engagement; preserve links back to the originating Opportunity, Lead/Prospect, proposal and payment record.

### Client project → creative production → public portfolio

1. Brief and brand profile are required before production.
2. Imported social analytics must record account authorization, source, reporting period, timezone, metric definitions and transformations.
3. Strategy and batch plan remain proposals until an authorized human approves them.
4. Each generated asset has a stable job and batch identity, source manifest, tool/model/template version and quality status.
5. Client delivery requires approval; public portfolio publication requires a separate rights and publication approval.
6. Client work is private by default. Internal concepts and prototypes must be labelled accurately.

## 5. ID, time, money and status conventions

- Use opaque immutable text IDs. UUIDv4 is acceptable for current JavaScript/Cloudflare compatibility; use the same representation across database rows, API payloads and event envelopes.
- Do not use email, company name, slug or array position as a primary key.
- Persist timestamps in UTC ISO 8601 with an explicit `Z` or offset. Display in the user's selected timezone; store reporting timezone where it affects interpretation.
- Persist monetary amounts as integer minor units plus an ISO 4217 currency code. Never use floating-point values for money.
- Use explicit, versioned status enums per entity. Do not reuse `leads.stage` for opportunities, payments, projects, tasks or deliverables.
- Model transitions deliberately. Terminal states, reopen rules and human approval requirements must be documented.
- Preserve raw source values only when needed and permitted; normalized values must retain provenance.

## 6. Tenant and permission contract

- Internal prospecting, agency operations and finance records are not client-visible by default.
- Every client-owned record must have an enforceable organization/tenant relationship, directly or through a verified parent.
- Every server read/write must authorize actor + action + resource + tenant. Hiding UI controls is not authorization.
- Client access is restricted to their own organization and explicitly assigned projects, briefs, approvals, reports and deliverables.
- Public website endpoints must return public-safe projections, not unrestricted operational rows.
- Audit events must not contain secrets, full payment credentials, raw session tokens or unnecessary personal data.
- Cross-tenant denial tests are a release gate before any client data or portal access is introduced.

## 7. Domain event envelope

Events are proposed contracts. They may initially be recorded in an application-owned table or emitted through an existing mechanism; no message broker is required at this stage.

Required envelope:

```json
{
  "event_id": "uuid",
  "event_type": "lead.created",
  "schema_version": 1,
  "occurred_at": "2026-11-10T08:00:00.000Z",
  "actor": {
    "type": "system",
    "id": "contact-api"
  },
  "tenant_id": null,
  "aggregate": {
    "type": "lead",
    "id": "uuid"
  },
  "correlation_id": "uuid",
  "causation_id": null,
  "idempotency_key": "contact-submit:uuid",
  "data": {
    "source": "website",
    "stage": "new"
  }
}
```

Rules:

- `event_id` is globally unique; consumers record processed IDs to prevent duplicate effects.
- `event_type` is namespaced and stable; incompatible payload changes require a new schema version.
- `occurred_at` is the domain occurrence time, not an assumed processing time.
- `actor` identifies the human, agent or system responsible. Agent actions also identify the initiating human/task where available.
- `tenant_id` is null only for genuinely global/internal events; tenant events must carry the owning tenant.
- `aggregate` identifies the entity whose lifecycle changed.
- `correlation_id` joins a business workflow across systems; `causation_id` points to the triggering event where applicable.
- `idempotency_key` is required for retried external operations and side effects.
- `data` contains the minimum necessary domain facts, not full personal briefs, secrets or raw provider payloads.

## 9. Reliability and transaction rules

- Persist a business state change and its corresponding outbox event atomically where the selected database/runtime supports it.
- If atomic outbox persistence is not available, document the failure window and use reconciliation; never pretend an API call and database write are one transaction.
- Consumers must be idempotent. Retrying an email, webhook, generation job or payment import must not create duplicate business records.
- Distinguish accepted, queued, processing, succeeded, failed, cancelled and partially completed job states.
- Retries require bounded attempts, backoff, terminal failure visibility and a safe manual recovery path.
- A provider timeout is an unknown outcome until reconciled; do not blindly repeat a non-idempotent operation.
- Keep event history and audit history conceptually distinct: domain events describe business facts; audit events describe who changed what and why.

## 10. Immediate implementation boundary

The next code slice should not create every proposed entity or install Temporal/NATS/Meilisearch.

1. Add dependency-free shared constants/validators for IDs, timestamps, existing lead stages and notification states.
2. Add tests that prove the shared contracts match migrations 0001–0003 and the current contact handler.
3. Define the proposed event envelope as a versioned JSON schema or equivalent validator.
4. Keep new CRM entities and migrations deferred until a concrete workflow requires them.
5. Inspect the actual Preview D1 schema before any migration is written or applied.

## 11. Acceptance criteria

- Existing lead fields and allowed enum values are accurately represented.
- Inbound Lead and researched outbound Prospect are distinct concepts.
- Organization, Contact, Opportunity, Client and Project are separate entities with explicit relationships.
- Client tenant boundaries and human approval gates are explicit.
- Event envelope has stable identity, version, actor, tenant, aggregate, correlation, causation and idempotency fields.
- No new external service, paid API, production migration or deployment is introduced by this contract document.
- The next implementation step can be completed and tested without changing the current public website behavior.
