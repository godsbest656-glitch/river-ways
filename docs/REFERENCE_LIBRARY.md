# River Ways Reference Library
**Last researched:** 9 October 2026  
**Scope:** Curated working directory for the disciplines required to design, build, launch, secure, grow, and maintain River Ways and future client websites.  
**Use:** Read primary standards first. Inspiration galleries and commercial tools are examples to study—not automatic recommendations or evidence of effectiveness.

> The public web is too large and changes too often for anyone to catalogue literally every reference. This is a deliberately comprehensive, versioned library across the disciplines needed for this programme. Add to it through the source-admission process at the end of this document.

## 1. How to use this catalogue

Resource classes:
- **Normative/primary:** standards, product documentation, official platform guidance, law/regulator sources. Prefer these for implementation and compliance decisions.
- **Research/practice:** research organisations and evidence-based UX/performance material. Use to inform hypotheses and validation.
- **Inspiration/benchmark:** galleries, portfolios and live products. Study specific patterns, inspect mobile behavior, and document why they work.
- **Tool/provider:** products that may need an account, budget, contract, API access, or privacy review.
- **Community:** repos, open-source libraries, and practitioner examples. Verify maintenance, license, dependencies, permissions, and security before use.

Each design reference should become a record: source URL, specific page/pattern viewed, user problem it solves, idea to adapt, details not to copy, accessibility/performance considerations, owner, date checked, and implementation status.

## 12. Source-admission and review process

Before adding a resource:
1. Confirm that the URL resolves and identify the original publisher.
2. Mark the type: standard, official documentation, research, gallery, provider, community repository, or legal source.
3. State the exact job it informs and which document/decision uses it.
4. Record licensing, account, payment, API, privacy or regional caveats where relevant.
5. Check the last updated date for standards/providers; record “reviewed on” separately.
6. Validate competing or contradictory claims against a primary source.
7. Add an owner and review cadence. Recheck volatile tools/platform APIs at least quarterly and before implementation.
8. Remove duplicates and archive superseded sources with a note rather than silently treating old guidance as current.
